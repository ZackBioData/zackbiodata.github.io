AWS Accounts & Account ID

  • Every AWS account has a unique 12-digit Account ID.
  • You can find it in the AWS Management Console (top-right account menu → “Account ID”), or in Support Center / My Account.

AWS Tools for PowerShell

  • AWS Tools for PowerShell exposes AWS APIs as PowerShell cmdlets.
  • Because PowerShell runs on .NET, you can script AWS operations (create S3 buckets, manage EC2, IAM, etc.) using familiar cmdlet patterns:
    • Get-, New-, Remove-, Set-, Write- against AWS services.

Amazon Resource Names (ARNs)

  • ARNs uniquely identify AWS resources across all regions and accounts.
  • Format: arn:partition:service:region:account-id:resourcetype/resource (varies by service).
  • You use ARNs in IAM policies, resource references, EventBridge rules, etc., to unambiguously specify the exact target.

AWS CloudShell

  • Browser-based shell inside the AWS Management Console.
  • Uses your current console credentials and is scoped per region.
  • Persists files in your home directory across sessions (per region).
  • Preinstalled with common tools (AWS CLI, Python, Git) for quick admin and scripting.

Infrastructure as Code (IaC)

  • IaC = define infrastructure in code to create/update/delete cloud resources repeatably.
  • Benefits: version control, review, sharing, drift detection, reproducible environments, faster automation.
  • Think of it as a blueprint of your cloud architecture.

Two main IaC options on AWS

AWS CloudFormation

  • Declarative templates in JSON or YAML (no XML).
  • “What you declare is what gets built.”
  • Great for explicit, auditable infrastructure definitions.

AWS Cloud Development Kit (CDK)

  • Imperative code in familiar languages (TypeScript/JavaScript, Python, Java, C#/.NET, Go) that synthesizes to CloudFormation templates.
  • Less verbose than raw templates; higher-level constructs can reduce boilerplate.
  • Because logic is code, be mindful of implicit defaults and ensure reviews to avoid misconfiguration.

Shared Responsibility Model

AWS (Security of the Cloud):
- Global infrastructure & hardware
- Physical datacenters, Regions, AZs, edge locations
- Physical security, power, networking
- Managed software layers (for managed services)
- Underlying compute, storage, databases, networking fabric

Customer (Security in the Cloud):
- Configuration of services (service controls, settings)
- Platforms & applications you run
- Identity & Access Management (IAM) (users, roles, policies, MFA)
- OS configuration (for EC2/self-managed)
- Network controls (Security Groups, NACLs, firewalls)
- Data protection
- Client-side encryption, server-side encryption options,
- In-transit protection (TLS), key management, data classification and lifecycle

TL;DR
- Customer is responsible for security in the cloud (your data, identity, configs).
- AWS is responsible for security of the cloud (the infrastructure and managed service underpinnings).

Key Takeaways

  • Account ID uniquely identifies your AWS account; check it from the console menu.
  • AWS Tools for PowerShell lets you script AWS with cmdlets over .NET.
  • ARNs = the precise way to reference resources across accounts/regions.
  • CloudShell gives you a ready-to-use, credentialed shell in-browser with per-region persistence.
  • CloudFormation (declarative) vs CDK (imperative): choose based on team preference and control; both end in CFN templates.
  • Shared Responsibility: AWS secures the platform; you secure configurations, identities, networks, and data.
